# Web System Design

## Overview

Opinionated defaults for web frontends, strongest for authenticated staff and admin apps, with a section for public content sites:
- a typed client over one backend;
- server state in a query cache, scoped to the signed-in account;
- shareable view state in the URL;
- a session cookie the page never reads;
- one shared component for every recurring screen pattern.

**Core principle:** the backend owns data and access; the frontend owns layout, flow and recovery. Mirror access in the UI only to *explain or hide* what the server would refuse anyway.

Library names (TanStack Query, Radix, shadcn, PostHog, Vite, Vercel) are examples of one stack. Keep the boundaries and swap the tools.

## When to Use

- Starting a new SPA, admin tool or site.
- Adding a big area (a new domain, a create flow, a dashboard) to an existing app.
- Choosing a rendering, state, auth or routing approach.
- Reviewing a frontend design doc.

## The Decisions

| # | Decision | Default |
|---|---|---|
| 1 | Rendering and hosting | Per route, by SEO, freshness and personalisation; an admin SPA can be static |
| 2 | Backend integration | A typed client generated from a pinned contract; compatibility across deployed versions |
| 3 | State | Server state in a query cache keyed by account and tenant; shareable, non-sensitive state in the URL |
| 4 | Session | A same-origin `Secure`, `HttpOnly`, `SameSite` cookie, plus CSRF protection |
| 5 | Session states | One gate for pending, signed in, signed out, required action and unavailable |
| 6 | Access | The server enforces; the UI shows capabilities and recovers from 403s |
| 7 | Multiple tabs | Account-change broadcast always; shared polling only when it pays |
| 8 | Interaction patterns | Sized by complexity and consequence |
| 9 | Design system | Semantic tokens, shared components, accessibility and i18n designed in |
| 10 | Environments | Required public config validated; non-production visibly labelled |
| 11 | Telemetry | Privacy decided before any SDK starts; free tier where it fits |

## 1. Rendering and hosting

- Choose per route: static, server-rendered, client-rendered or mixed. The deciding factors are SEO, first-load speed, personalisation, caching and hosting.
- **An authenticated admin SPA** can be statically hosted and talk to its backend directly. Add a BFF or a framework server only when it improves session security (same-origin cookies) or aggregation.
- **A public site** needs SEO and performance decisions. See [A content site](#a-content-site).

## 2. Backend integration

- **One backend per frontend where possible**, reached through a **typed client generated from a pinned API contract**, regenerated by a script and never edited by hand. Reuse its types instead of hand-writing them.
- Generated types catch drift at build time, not for an old bundle still open in a browser. Define how long old frontend versions keep working against a new backend, and what happens when they stop (prompt to reload).
- **Components don't call HTTP.** Transport and server-state code live in the project's data layer: query hooks per domain, route loaders or server components. Keep query keys in one place. Add mappers only when wire and UI shapes really differ.

## 3. Where state lives

| State | Lives in |
|---|---|
| Server data | The query cache, keyed by **account, tenant or workspace, and every input** that shapes the response |
| Shareable navigation (tab, page, sort, non-sensitive filters, the open record's ID) | The URL |
| Sensitive search terms and form values | Memory, never the URL |
| Per-tab context (which workspace this tab shows) | `sessionStorage`, with the last choice in `localStorage` only as the starting value for new tabs |
| Drafts of long flows | Memory by default. Use browser storage only for fields approved to be stored there, scoped to the account, with an expiry, and cleared on submit, logout or account switch. Sensitive drafts that must survive a reload go to an authenticated server draft |
| Other global client state | None, until a concrete cross-component need appears |

**Invalidating the cache is not isolation.** On logout or an account change:
- cancel in-flight requests;
- remove cached and persisted data for the old account;
- bump a session generation, so late responses are dropped.

On a workspace or tenant switch, render only that context's cache. The backend checks membership. A header naming the tenant is a request, not authority.

## 4. Sessions

- **Prefer a same-origin session cookie:** `Secure`, `HttpOnly`, an explicit `SameSite`, and a narrow host and path. The backend defines rotation, idle and absolute expiry, and server-side logout.
- **`HttpOnly` is not CSRF protection.** Protect state-changing requests with the framework's CSRF mechanism plus origin checks. Safe methods never change state.
- **If you must go cross-origin,** allowlist exact origins and turn on credentials in the HTTP client (`withCredentials` in axios, `credentials: 'include'` in fetch). CORS is not authorisation.
- In development, mirror the production topology (a dev-server proxy for `/api` when production is same-origin).
- Keep primary credentials out of browser storage. A short-lived ticket for a third-party SDK can live in memory.
- **Account guard:** writes carry the expected account (`X-Expected-User`). The backend answers `409` if another account is now signed in from another tab. This catches account races; it is neither authentication nor CSRF defence.

## 5. Session states

Centralise session handling in one gate with five states:

1. **Pending** → a loading state.
2. **Unavailable** (the session check failed with a network or server error) → a retry screen, never a false sign-out.
3. **Signed out** → sign-in. Any protected path redirects with `?next=`, validated as an allowed same-origin relative path.
4. **Required action** (`mustChangePassword`, accept terms) → only that screen. The backend enforces the same restriction on its APIs.
5. **Signed in** → the app layout, every page behind an access guard.

Public routes that need no session (shared links `/r/:token`, anonymous surveys `/s/:slug`) render outside the gate.

**401 handling:** one handler for protected requests only, excluding sign-in, session discovery and public calls. It coalesces concurrent 401s, keeps recoverable work, and tells apart lost authentication (401), forbidden (403), network failure and server failure.

## 6. Access

- Fetch the caller's **effective capabilities** for the current account and tenant (`GET /me/permissions`). Use them to hide or explain unavailable pages and actions. Refetch them on account, tenant or grant changes, and treat a `403` as a signal to refresh them.
- A **route → capability map** plus an access guard on each page is a good shape. Share the permission identifiers with the backend, but don't reimplement its logic. Pages don't map one-to-one to endpoints.
- Show "You don't have access", not a blank page.

## 7. Multiple tabs

- **Always:** broadcast logout and account changes to every tab (`BroadcastChannel`, with a `storage` event fallback), namespaced by account and session generation.
- **When duplicate traffic is measured:** let one tab own polling or a live connection, using Web Locks for ownership, leases with expiry and takeover, and per-context subscriptions. Other tabs reuse its results. Each tab must still work if coordination is unavailable.
- Build it once and reuse it.

## 8. Interaction patterns

Size the interaction by complexity, consequence and how easily it can be undone:

| Pattern | Use for | Shape |
|---|---|---|
| **Full-page flow** | Substantial creates, bulk changes, anything that sends messages or moves money | Its own URL, drawn over the page you came from; steps, a sticky footer, a review step before anything irreversible; drafts kept where losing them would hurt |
| **Inline section edit** | Changing the record you're looking at | A section's Edit turns values into fields with Save and Cancel; unsaved changes guarded |
| **Detail page** | Anything you'd link to or act on in steps | Its own route, a status pill, key facts, tabs, activity |
| **Danger zone** | Irreversible or high-impact actions (delete, revoke) | Permission-gated; a typed confirm for irreversible ones; a reason only when audit needs one |
| **Dialog** | Short, focused tasks: confirm, pick one thing, a small field | The button names the verb; focus returns on close |
| **Undo** | Recoverable changes | A toast with Undo beats a confirm |

Show server validation and conflict errors inline. Prevent double submits with server idempotency, not just a disabled button. The server records audit events, so keep free-text personal data in reasons to a minimum.

## 9. Design system, accessibility and language

- **Semantic tokens on `:root`** (colour roles, radius, spacing, type). Components use tokens, never raw colours. A quiet admin look (neutral panels, hairline borders, brand colour for primary actions, colour otherwise only for status) is a good preset for staff tools; choose a direction that suits the product.
- **One shared component per recurring need** (page header, table panel, filters, inline edit, flow, status pill, empty, loading and error states). Search before building. A primitive library (Radix, shadcn) sits underneath.
- **A written guide (`DESIGN.md`).** When it and the code disagree, settle which is intended, then fix the guide or the code. Keep unrelated migrations out of the current change.
- **Accessibility is a design input.** Target WCAG 2.2 AA:
  - keyboard paths, with visible focus that returns to where it was;
  - semantic forms, with errors announced;
  - contrast, zoom and reflow, and reduced motion.

  Primitives don't guarantee an accessible flow.
- **Language and locale:** decide on translation, RTL, text expansion, and date, number, currency and timezone formats before labels and formatted values spread through components.

## 10. Environments and security headers

- **Validate required public config** at build or startup. An explicit same-origin `/api` is valid. A missing API URL must never fall back to the production host.
- **Everything in the browser bundle is public** (`VITE_*`, `NEXT_PUBLIC_*`). Secrets stay on the server.
- **Make non-production obvious with a visible label and one switch:**
  - set `data-env="staging"` on `<html>` at boot and override the brand tokens under `:root[data-env='staging']`;
  - colours computed in JS (charts) read one constant chosen once;
  - no `isStaging ? … : …` scattered through components.
- **Deploys:** follow the host's policy. Deploy the environment branches only, isolate preview credentials and data, and know how to roll back.
- **Headers:**
  - HTTPS and HSTS;
  - a Content Security Policy, including framing rules;
  - `X-Content-Type-Options` and a referrer policy.

  Treat CMS and user HTML as untrusted and sanitise it.

## 11. Telemetry

- **Decide privacy before any SDK starts:** environment, route and consent. Excluded routes (anonymous public pages, capability links) start no analytics or error SDK at all.
- Autocapture and session recordings stay off unless decided. Use an allowlisted event schema. Scrub URLs, tokens, form values and user content from events and errors. Reset the telemetry identity on logout.
- A free tier of PostHog or similar is a good fit for product analytics and error tracking. A free tier is not a privacy guarantee.
- Route- and root-level error boundaries show a recoverable page. Async and event-handler errors need their own handling.

## A content site

When the public site is a CMS app (for example Next.js with a headless CMS):
- The CMS owns editorial content. Catalogue, pricing, checkout and identity sit with their real owners, which may also be the CMS.
- **Caching:** public published content can use shared caches with publish-triggered tag invalidation. Authenticated, preview and personalised reads stay uncached or are partitioned by everything that shapes them.
- **Checkout:** guests can buy. Link orders to an account at purchase, or through an explicit claim flow bound to the order. A matching email alone is not enough.
- **Payment webhooks** follow the backend's rules: verify, record durably, fulfil idempotently.
- **Magic links** (order view, cart recovery) are bearer capabilities:
  - high-entropy tokens stored as HMACs, scoped to one record and action, with an expiry, revocable, and single-use where it matters;
  - kept out of logs, analytics, referrers and caches;
  - not consumed by a link-preview `GET`.
- **Member session revocation** (bumping a session version) works only if every authenticated request checks the current version.

## Write the design as

1. **Summary**, and the **Problem** it solves.
2. **Rendering and routes:** the route list, marking public routes, flows and how each renders.
3. **Data:** endpoints, hooks or loaders, query keys and their scope.
4. **State:** what's in the cache, the URL, memory and storage, and what's cleared on logout.
5. **Session and access:** the cookie and CSRF setup, the gate states, and the capability for each route.
6. **Patterns:** each action → flow, inline edit, detail, danger zone, dialog or undo.
7. **Validation and rollout:**
   - tests for session expiry, account and tenant switching, permission changes and API failures;
   - browser tests of the main flows, reload and back;
   - keyboard and screen-reader checks;
   - performance budgets;
   - support for old bundles, and rollback.
8. **Open questions**, each with a recommended answer.

## Red Flags

- `fetch` or `axios` inside a component.
- A hand-written type the generated client already has.
- Query keys with no account or tenant in them.
- Cache invalidation used as the logout cleanup.
- Personal search terms in the URL.
- A token in `localStorage`, or drafts that outlive logout.
- Cookie sessions with no CSRF protection.
- A 401 handler that signs people out when the network blips.
- Access logic that exists only in the frontend.
- Analytics that start before consent and route are known.
- `isStaging ? … : …` in components.
- An empty env var that means production.
