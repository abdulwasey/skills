# Web System Design

## Overview

A thin client over one backend: generated API client, server state in a query cache, view state in the URL, a cookie session the page never touches, and one shared component for every recurring screen pattern.

**Core principle:** the backend owns data and access; the frontend owns layout and flow. Never duplicate one in the other, except to *hide* what the server would refuse anyway.

For the services behind it, see `backend-system-design` in this repo. For a mobile client, see `app-system-design`.

## When to Use

- Starting a new SPA, admin tool or site.
- Adding a big area (a new domain, a create flow, a dashboard) to an existing one.
- Choosing a state, auth or routing approach.
- Reviewing a frontend design doc.

Not for: line-level React review (see `react-review`) or visual design critique (see `design-audit`).

## The Decisions

| # | Decision | Default |
|---|---|---|
| 1 | Backend | One backend per frontend, reached only through a generated client |
| 2 | State | Server state in a query cache, view state in the URL, almost nothing else |
| 3 | Session | httpOnly cookie set by the backend; no tokens in JavaScript |
| 4 | Boot and gates | One session gate decides public, loading, signed out, must-act and signed in |
| 5 | Access | The server enforces; the frontend mirrors the route→permission map to hide |
| 6 | Multiple tabs | One leader polls and broadcasts; an account change resets every tab |
| 7 | Interaction patterns | Flows, inline edits, detail pages, danger zones; modals only for small things |
| 8 | Design system | Tokens on `:root`, one component per recurring need, a written rule book |
| 9 | Environments | Required config fails loudly; staging looks different through one switch |
| 10 | Analytics | Privacy-first and on a free tier |

## 1. One backend, one generated client

- A staff or admin SPA has **no server of its own**. All data comes from one backend.
- Call it through a **client generated from the backend's OpenAPI spec** (regenerated by a script, never edited by hand). Types come from the same place, so a contract change breaks the build, not production.
- **Components never call HTTP.** Each domain has one hook file (`query/<backend>/use<Domain>.ts`). Query keys live in one file.
- A hand-written client is allowed only for a service with no spec, and stays in one file.

## 2. Where state lives

| State | Lives in |
|---|---|
| Anything from the server | The query cache (TanStack Query), keyed in one place |
| Tabs, filters, pagination, search, the open record | The URL (`useUrlTab`, `useUrlPagination`, `useFilterSync`) |
| Per-tab context (which workspace or product this tab shows) | `sessionStorage`, with the last choice in `localStorage` only as the starting value for new tabs |
| Unsaved drafts of long flows | Local storage keyed by flow and user |
| Anything else global | Nothing. No global store until a second real need appears |

Switching a context that changes what data means (workspace, product, tenant) invalidates the whole cache and sends that context to the backend on every request (a header).

## 3. Sessions

- The backend sets an **httpOnly session cookie**. The frontend sends it with `withCredentials` and never holds a token.
- Locally, the dev server proxies `/api` so the cookie is first-party, just like in production.
- **One global 401 handler** redirects to sign-in with `?next=<path>&expired=1`.
- **Account guard:** writes carry the expected account (`X-Expected-User`), and the backend answers `409` if another account is now signed in from another tab. Responses for a different account are dropped.

## 4. Boot order and the session gate

Boot does the env marker, interceptors and analytics, then the providers: analytics → error boundary → query client → context → account boundary → router.

One `SessionGate` picks what renders:
1. Public routes that need no session (shared links `/r/:token`, anonymous surveys `/s/:slug`).
2. Session pending → a spinner.
3. No session → the landing and sign-in page; any other path redirects with `?next=`.
4. Session with a required action (`mustChangePassword`) → only that screen.
5. Otherwise → the signed-in layout, with every page behind an access guard.

## 5. Access

- The backend is the gate. The frontend reads the caller's permissions once (`GET /me/permissions`) and hides what they'd be refused.
- Keep a **path → permission map** (`PAGE_PERMISSIONS`) that mirrors the backend's route gates, and put every page behind an `AccessGuard`. Show "You don't have access", not a blank page.
- Routes that belong to one workspace switch the tab to it, or explain why they can't.

## 6. Multiple tabs

Staff keep many tabs open, so plan for it:
- **Leader election** (Web Locks, then `BroadcastChannel`, then `localStorage` as a fallback). Only the leader polls; the others reuse its results from a cross-tab bus.
- **Account-changed broadcast:** signing in as someone else in one tab resets every tab.
- Build this once and reuse it. Never add a second cross-tab mechanism.

## 7. Interaction patterns

Decide the pattern by what the action does, not by habit:

| Pattern | What it is | Use for |
|---|---|---|
| **Full-page flow** | Its own URL, drawn over the page you came from, with steps, a sticky footer (Cancel, Back, Continue) and a review step before anything is saved | Creating records, bulk changes, anything that sends messages or touches money |
| **Inline section edit** | A section's Edit turns values into fields with Save and Cancel; one section at a time; unsaved changes guarded | Changing the record you're looking at |
| **Detail page** | Its own route with Back and an "n of N" pager, a status pill, key facts, tabs, Activity and Comments | Anything you'd link to or act on in steps |
| **Danger zone** | A permission-gated section at the bottom of a record; typed-name confirm plus a reason | Delete, archive, exit, revoke |
| **Modal** | Confirm one consequential action, pick one thing, fill one small field. The button names the verb; Cancel takes focus | Only those |

Every destructive action has a reason field and lands in the record's activity history.

## 8. Design system

- **Tokens on `:root`** (colour, radius, spacing, type). Components use tokens, never raw colours.
- **One quiet look:** neutral panels and hairline borders, the brand colour for primary actions, colour otherwise only for status.
- **One shared component per recurring need** (page header, table panel, filters dialog, inline edit, create flow, status pill, empty and error states). Search before building a new one.
- **A written rule book** (`DESIGN.md`). When the rule book and the code disagree, the rule wins: fix the code in the same PR.
- Use a primitive library (Radix or shadcn on Tailwind) underneath, and keep your own patterns on top.

## 9. Environments

- **Required config fails loudly.** An empty `VITE_API_URL` must stop the build or show an error page. It must never fall back to the production URL.
- **Staging looks different through one switch:** set `data-env="staging"` on `<html>` at boot, and override the brand tokens under `:root[data-env='staging']`. Values computed in JS (chart colours) read one constant chosen once. No conditionals spread through components.
- **Deploys:** the host deploys only the environment branches (`staging`, and the default branch once production is wired), not every branch (`git.deploymentEnabled`). Preview builds are opt-in.

## 10. Analytics and errors

- PostHog (or similar) on its free tier, for product analytics and error tracking. Autocapture and session recordings stay off unless decided. Events are consent-gated where the law needs it.
- **Anonymous public pages send nothing.**
- Never put personal data in URLs, query strings, event properties or logs.
- An error boundary at the root reports to the tracker and shows a recoverable page.

## A content site, if there is one

When the public site is a CMS app (Next.js with a headless CMS):
- The CMS owns content, catalogue and checkout. Other clients read its public listing API.
- Cache server reads with tags, and revalidate on publish.
- Checkout works for guests; orders join to members by verified email.
- Payment webhooks are verified, recorded, then fulfilled.
- Magic links (order view, cart recovery) are random tokens stored as HMACs, with an expiry.
- Member sessions can be revoked by bumping a session version.

## Write the design as

1. **Summary**, and the **Problem** it solves.
2. **Routes:** the route list, with public routes and flows marked.
3. **Data:** which backend endpoints, through which hooks, with which query keys.
4. **State:** what lives in the cache, the URL and storage.
5. **Access:** the permission per route, and what's hidden.
6. **Patterns:** each action → flow, inline edit, detail page, danger zone or modal.
7. **Open questions**, each with a recommended answer.

## Red Flags

- `fetch` or `axios` inside a component.
- A hand-written type for something the generated client already has.
- A global store holding server data.
- A filter or tab that resets on reload, because it isn't in the URL.
- A token in `localStorage`.
- Access logic that exists only in the frontend.
- A modal holding a five-field create form.
- A delete with no confirm and no reason.
- `isStaging ? … : …` in components.
- An empty env var that means production.
